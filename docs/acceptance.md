# AiSana B2B - руководство по приемке

https://demo-not-real-aisana.onrender.com
Версия от 19.11.2026 (четверг), ветка `feat/b2b`, HEAD на момент сдачи - `f25648a`.
Постановка: «на портале должны быть карточки решений; представитель бизнеса авторизуется
и смотрит нужные ему решения». Механика диалога - порт внутреннего конструктора диалога
(Business Challenge Builder), проверена на 30 задачах с реальных KZ-рынков.

Документ для тех, кто принимает работу: что добавлено, под какими учётками входить, как
идёт запрос компании от первого входа до ответа вуза, что проверить руками. За неделю
16-19.11 к фазам A-C добавлены тёмная тема, полная локализация ru/kz, меры безопасности
и временный публичный демонстрационный стенд - они расписаны в разделах 13-17. Документ
открыт в репозитории на время ревью; после показа - закрыть или удалить.

Сокращения: ПДн - персональные данные; ИИН - индивидуальный идентификационный номер;
БИН - бизнес-идентификационный номер; IBAN - международный номер банковского счёта;
SLA - уровень сервиса (соглашение об уровне обслуживания); TTL - время жизни;
COOP/CORP - заголовки изоляции контекста окна; CI - конвейер автоматических проверок;
NDA - соглашение о неразглашении; SSR - рендеринг на сервере.

## 1. Что добавлено

AiSana - закрытый каталог ИИ-проектов вузов Казахстана. Ветка добавляет в него компании как
третью сторону: компания смотрит готовые университетские решения и через оператора портала
выходит на вуз-разработчик.

| Фаза | Коммит | Что даёт |
|---|---|---|
| A. Роль и каталог | `6a69982` | роль `BUSINESS_REP`, компания у учётки; бизнес видит каталог опубликованных решений (`/projects`) без почты руководителей и без ссылок на правку |
| B. Запросы по решению | `2243cb5` | компания запрашивает демо, консультацию, пилот или внедрение; оператор разбирает и передаёт вузу; вуз отвечает |
| C. Помощник подбора | `59a9bfe` | диалог с ИИ (порт конструктора BCB): компания описывает задачу своими словами, помощник уточняет её и подбирает решения из каталога; итог уходит оператору |
| D. Флаг витрины + доступ | `dcca5b1` | флаг «доступно бизнесу» (`availableForIntegration`) на проекте: модератор (ADMIN, EDITOR) открывает решение бизнесу, не публикуя ничего лишнего; витрина - `/business/solutions`; заодно закрыты недостатки контроля доступа |
| E. Тёмная тема | `b20d4f9`, `34dd98b`, `9d90b94`, `8a90991`, `2d077a4` | системная / светлая / тёмная, карта и графики под тему, контраст muted-текста, Best Practices и ИИ-резюме в тёмной теме, колесо мыши в шапке |
| F. Локализация ru/kz | `62567f7`, `fc11380`, `f26cb2e`, `95777cf`-`1b96372`, `0c8330a` | весь интерфейс на двух языках (cookie + SSR), Excel-выгрузка, поиск, помощник подбора, подписи технологий и тегов по словарю |
| G. Безопасность, нед. 2 | `52ea372`, `64cf514`, `9de2b71` | sha256-токены сессий, `__Host-`-cookie, аудит-события LOGIN/LOGOUT/EXPORT с IP и User-Agent, хранение записей - 365 дней, ограничения на загрузку и выгрузку |

«Карточки» здесь - существующие карточки проектов (`/projects`); витрина для бизнеса -
отдельная страница `/business/solutions` с проектами, которые модератор открыл для интеграции.

и помощник. Полная часть - B2B-поля карточки - ждёт решения (раздел 18).

## 3. Учётные записи

Демо-учётки создаёт `pnpm db:seed:demo`; пароль берётся из `DEMO_PASSWORD` (без него сид не
запускается). Доступ к демонстрационному стенду - в `tempusersrender.md`, который
открывается вместе с документом.

| Роль | Учётка | Что смотреть |
|---|---|---|
| Бизнес | `demo-business@demo.kz` - «ДЕМО Компания» | каталог, форма запроса на карточке, «Мои запросы», «Подбор решения» |
| Оператор | `demo-admin@demo.kz` (ADMIN), `demo-editor@demo.kz` (EDITOR) | очередь «Запросы бизнеса», передача вузу, почта руководителя на карточке видна |
| Вуз | `demo-rep@demo.kz` - представитель ENU | видит только переданные ему запросы по проектам ENU, отвечает компании |
| Просмотр | `demo-viewer@demo.kz` | к запросам и помощнику доступа нет |
| Администратор стенда | `admin@mnvo.kz` (ADMIN) | полный доступ, создан штатным `prisma/seed.ts`; пароль - из `ADMIN_PASSWORD` (если не задан - сгенерирован и напечатан в лог) |

Удобные связки:

- `demo-business` + `demo-admin` + `demo-rep` - полный путь запроса (раздел 8, сценарий 3).
- `demo-business` → «Подбор решения» → «Прежние подборы» - готовая потребность про конвейеры.

Саморегистрации нет, как и раньше. Компания просит доступ на `/contacts` (тема «Запросить
доступ (вуз или компания)»), администратор создаёт учётку с ролью «Представитель бизнеса» и
обязательным полем «Компания».

## 4. Роли и полномочия

| | Бизнес (`BUSINESS_REP`) | Оператор (ADMIN, EDITOR) | Вуз (`UNIVERSITY_REP`) | `VIEWER` |
|---|---|---|---|---|
| Стартовый экран | `/business/solutions` (витрина; админка закрыта редиректом) | `/admin` | `/admin` | `/admin` |
| Каталог | опубликованное в `/projects` и на витрине, без `leadEmail` | всё, с почтой | всё своего вуза + опубликованное | опубликованное, с почтой |
| Ссылки «Редактировать / Добавить» | скрыты | видны | для своего вуза | скрыты |
| Запрос по решению | создаёт (по опубликованному проекту) | - | - | - |
| Видит запросы | только свои | все | только переданные по проектам своего вуза | - |
| Меняет запрос | - | любой статус, проект (до передачи), обе заметки | «Передан вузу → В работе / Отклонён», «В работе → Завершён / Отклонён», ответ вуза | - |
| Помощник подбора | да, видит только свои потребности | да (для проверки) | нет (403 / редирект) | нет |

Каждая запись проверяется на сервере (`requireApiRole`, `canChangeStatus`, `visibleRequestsWhere`);
скрытая кнопка - не защита. Чужой запрос или чужая потребность отдают 404, как несуществующие.
Создание и изменение запросов пишутся в журнал аудита.

## 5. Пайплайн

### 5.1 Сквозной путь компании

```
/contacts: заявка на доступ (Feedback, тема ACCESS_REQUEST)
        │  администратор создаёт учётку BUSINESS_REP с компанией
        ▼
вход → /business/solutions (витрина: опубликованные решения, открытые модератором)
        │   общий каталог опубликованного - /projects
        ├─► карточка проекта → «Интересует решение?» ──────────────┐
        │     тип: демо / консультация / пилот / внедрение          │
        │                                                            ▼
        └─► «Подбор решения» → диалог → подборка ──► «Отправить оператору»
              (проект необязателен)                                  │
                                                                     ▼
                                                      IntegrationRequest (NEW)
                                                                     │
                                         оператор /admin/requests ───┤
                                         привязывает проект, если нет│
                                                                     ▼
                                              SENT_TO_UNIVERSITY (forwardedAt)
                                                                     │
                                           вуз /admin/requests ──────┤
                                           ответ вуза → компании     ▼
                                                 IN_PROGRESS → DONE
компания следит за статусом и ответом вуза в «Мои запросы» (/business/requests)
```

Прямых контактов стороны не получают: почту руководителя проекта бизнес не видит, контакт
компании виден оператору и вузу внутри запроса. Уведомлений нет - оператор связывается с
вузом вне портала.

### 5.2 Статусы запроса

```
NEW ──► IN_REVIEW ──► SENT_TO_UNIVERSITY ──► IN_PROGRESS ──► DONE
 │          │               │ (вуз)              │ (вуз)
 └──────────┴───────────────┴────────────────────┴──────► DECLINED
```

| Правило | Зачем |
|---|---|
| Передать вузу можно только запрос с проектом | без проекта неизвестно, какому вузу он адресован |
| Проект меняет только оператор и только до передачи | иначе запрос молча ушёл бы к другому вузу |
| Вуз видит запрос по `forwardedAt`, а не по статусу | «отклонён оператором до передачи» не должен попасть вузу |
| Заметку оператора видят только ADMIN/EDITOR; ответ вуза - все участники | внутренняя переписка не уходит компании |

### 5.3 Ход помощника подбора

Каждый ход - `POST /api/need` (первое сообщение) или `POST /api/need/[id]/turn`:

```
сообщение компании (2-2000 символов)
  │ 1. лимиты: 30 ходов в час на пользователя; не больше 12 ходов на потребность
  │ 2. findSensitive: ИИН (с контрольной цифрой), карта (Luhn), телефон, email
  │      найдено → 422 с маскированными фрагментами, в модель текст НЕ уходит
  ▼
analyzeDialog: Gemini разбирает ВЕСЬ диалог заново
  │   ответ - JSON по схеме: 7 полей {status, value, quote} + вопросы
  │   цепочка моделей при 429/503/таймауте 20 с; на весь разбор 45 с
  │   ни одна модель не ответила → 503, ход не засчитан, пустая потребность удаляется
  ▼
verifyAnalysis: цитата ищется дословно в репликах КОМПАНИИ
  │   нет цитаты → поле «нет» (за компанию ничего не придумывается)
  ▼
scoreFields: полнота 0-100 по весам (код, не модель)
selectQuestions: 1-й ход - не меньше трёх вопросов о самых весомых пробелах, дальше до трёх
fieldChanges: какое поле и на сколько поднял этот ответ
  ▼
запись с оптимистичной блокировкой по turnCount (параллельный ход → 409)
  ▼
matchProjects: поиск каталога по подтверждённым «задача / проблема / результат»
  (пока их нет - по репликам компании), порог оценки 10, до 5 решений
```

Поля и веса: задача и процесс 20, доступные данные 20, проблема сейчас 15, ожидаемый результат 15,
где должно работать 10, интеграции 10, масштаб и сроки 10. Статус «есть» - полный вес,
«слабо» - половина. Порог готовности 80 - рекомендация, отправить можно в любой момент.

### 5.4 Отправка оператору

`POST /api/need/[id]/send` в одной транзакции закрывает потребность (`SENT`) и создаёт запрос
типа «Консультация» с `needId`. Текст запроса собирает код: только подтверждённые поля
(«слабые» помечены «без подробностей»), полнота и комментарий компании. Вуз видит этот текст,
а не диалог. После отправки новые ходы - 409.

## 7. Демо-данные

`pnpm db:seed:demo` (запускать с хоста: сид импортирует код из `src/`). Повторный запуск
обновляет записи, а не дублирует; дату передачи и заметки при этом не сбрасывает.

| id | Проект (вуз) | Тип | Статус | Что показывает |
|---|---|---|---|---|
| `demo_req_new` | Предиктивная диагностика горного оборудования (KBTU) | Демо | Новый | очередь оператора; вуз KBTU его не видит |
| `demo_req_forwarded` | Жасанды интеллект негізіндегі оқу жүйесі (ENU) | Пилот | Передан вузу | виден `demo-rep`, ждёт его решения |
| `demo_req_progress` | тот же (ENU) | Консультация | В работе | ответ вуза виден компании |
| `demo_req_declined` | ИИ-ассистент для подбора персонала (SATU) | Внедрение | Отклонён оператором до передачи | вуз его не видит, заметку оператора компания не видит |
| `demo_need_mining` | - | потребность | собирается, 1 ход | горнодобывающая компания, прогноз поломок конвейеров; подборка находит `demo_prj_mining` |

На витрине `/business/solutions` - 4 проекта: `demo_prj_weld` (сварка), `demo_prj_mining`
(горная диагностика), `demo_prj_hr` (подбор персонала), `demo_prj_health` (медицина).
`demo_prj_edu_kz` и `demo_prj_energy` опубликованы, но модератором не открыты, поэтому
видны только в общем каталоге `/projects`; `demo_prj_draft` - черновик. Флаг управляет только
показом на витрине: запрос можно отправить с карточки любого опубликованного проекта.

Удалить демо: `DELETE FROM integration_requests WHERE id LIKE 'demo_%'; DELETE FROM business_needs WHERE id LIKE 'demo_%';`
(плюс прежние запросы для проектов и вузов - в шапке `prisma/seed-demo.ts`).

## 9. Как это работает - технически

**Стек** прежний: Next.js 15 (App Router), Prisma 5 + PostgreSQL 16, Tailwind 3, zod 4,
`@google/generative-ai`. Новых зависимостей нет (zod 3 → 4 - апгрейд ради чистого аудита,
см. ниже; overrides в `pnpm-workspace.yaml`). Дизайн - классы
и компоненты AiSana (карточки `rounded-xl border-slate-200`, бейджи статусов, формы как в
`FeedbackForm`); из внутреннего прототипа перенесены только логика и раскладка «чат слева, карточка справа».

**Миграции** (безопасны для живой БД; все, кроме перехеширования сессий, аддитивные):

| Миграция | Что делает |
|---|---|
| `20261116074352_add_business_rep_role` | `ALTER TYPE "UserRole" ADD VALUE 'BUSINESS_REP'` |
| `20261116074400_add_user_organization` | `users.organization TEXT NULL` |
| `20261116074738_add_integration_requests` | таблица `integration_requests`, два перечисления, FK `SET NULL` на проект и пользователя |
| `20261116080727_add_business_needs` | таблица `business_needs` (FK `CASCADE` на пользователя), `integration_requests.needId` (`SET NULL`) |
| `20261117120000_add_available_for_integration` | `projects.availableForIntegration BOOLEAN NOT NULL DEFAULT false` - модератор (ADMIN/EDITOR) помечает решение как доступное бизнесу |
| `20261118130000_hash_session_tokens` | `CREATE EXTENSION pgcrypto`; просроченные сессии удаляются, живые токены перехешируются в sha256 на месте; cookie при этом переименована, поэтому все один раз входят заново (раздел 19, п. 10) |
| `20261118140000_audit_context` | `audit_logs.ip TEXT`, `audit_logs.user_agent TEXT` (обе с `IF NOT EXISTS`) |

**Код.**

```
src/lib/publication.ts          canSeeLeadContacts, withoutLeadContacts
src/lib/integration-requests.ts visibleRequestsWhere, canViewRequest, canChangeStatus, canSetProject, подписи
src/lib/need-builder/           readiness, quotes, questions, diff, sensitive (перенос из прототипа)
                                prompts, analyze (Gemini + zod), match (поиск каталога), summary, service (Prisma)
src/app/api/requests/           POST, [id] PATCH
src/app/api/need/               POST, [id]/turn POST, [id]/send POST
src/app/business/               requests, assistant, assistant/[id]
src/app/admin/requests/         очередь оператора и вуза
```

**API.**

| Метод и путь | Роли | Ответы |
|---|---|---|
| `POST /api/requests` | BUSINESS_REP | 201; 400 (zod); 403; 404 (проект не опубликован); 429 (10/сутки) |
| `PATCH /api/requests/[id]` | ADMIN, EDITOR, UNIVERSITY_REP | 200; 403 (переход не разрешён); 404 (не виден) |
| `POST /api/need` | BUSINESS_REP, ADMIN, EDITOR | 201; 422 (ПДн); 429 (30 ходов/час); 503 (модель недоступна) |
| `POST /api/need/[id]/turn` | те же | 200; 404; 409 (закрыта, лимит 12 ходов, параллельный ход); 422; 429; 503 |

Форма ответов `/api/projects`, `/api/universities`, `/api/hearings` для прежних ролей не менялась;
для бизнеса в них зануляется `leadEmail`.

**zod 3 → 4.** Проверено по аудиторским базам (19.11.2026):
находка `GHSA-mrhx-c7xc-m3w5` («oversized constrained collections», CVSS 8.2, GitHub Advisory,
патч ≥4.6.6) ловила все номера zod ≤4.6.5 - и 3.x тоже. Но CVE-2023-54404, которому она
соответствует, **отклонена** CNA VulnCheck 28.10.2026: «рост памяти пропорционален уже
выделенному JSON.parse-входу, достижимо только без лимита размера запроса, это ожидаемое
поведение валидатора, а не дефект Zod». NVD/CVE-объект - rejected. Итого: апгрейд выполнен
как гигиена и обнуление находок аудита, а не как закрытие принятой уязвимости; в коммитах
и PR это не должно фигурировать как security-fix. Для zod 3.x `pnpm audit` даёт ровно эту
одну находку - всё, других известных проблем у zod 3 нет. Текущая версия - 4.6.7, аудит: 0.

**Gemini.** Задача `'need'` идёт как сложная, `MODEL_MAIN = gemini-3.6-flash`; цепочка
`GEMINI_MODEL_FALLBACKS = gemini-3-flash-preview, gemini-3.6-flash, gemini-3.5-flash-lite, gemini-3.1-flash-lite` (дубликат основной снимается дедупликацией). Простая задача (резюме)
стартует с lite: `gemini-3.5-flash-lite` → lite-пул → flash-цепочка. Квота делится с ИИ-поиском
модераторов: у flash ~20 запросов/сутки, у lite ~500 (по AI Studio на 18.11.2026); при 429/503
запрос переносится на следующую модель, весь разбор ограничен ~45 с; ход не засчитывается,
если ни одна модель не ответила. Проверка текущего ключа 18.11.2026: `gemini-3.6-flash` и
`gemini-3-flash-preview` отвечают 200; `gemini-3-flash` не существует (404), `gemini-2.5-flash`
недоступен новым аккаунтам. На бесплатной квоте это даёт более долгий ответ, но не отказ:
поиск и помощник работают. Без ключа
`GEMINI_API_KEY` код вообще не вызывает модель: ИИ-поиск и помощник отвечают «недоступно».
Ключ считайте скомпрометированным: он исторически фигурировал в открытой истории git -
на проде поставить НОВЫЙ, старый отозвать в AI Studio. Актуальные значения - в `.env.example`.
Ходы помощника не кэшируются; кэш ИИ-поиска хранит ответ модели и хэши промпта и данных,
но не исходный текст запроса; в ключ добавлен язык интерфейса. Доступность моделей с ключом проекта (проверка 16-18.11.2026):

| Модель | Результат |

| `gemini-3.6-flash` (`gemini-3.5-flash` - его псевдоним) | работает, 14-24 с |
| `gemini-3.1-pro-preview`, `gemini-4-argon`, `gemini-4-carbon` | 429 (квота) |

| `gemini-3.8-flash` | 503 |

Поэтому `gemini-3-flash` заменён на `gemini-3-flash-preview` в коде, `.env.example` и `docker-compose.yml`.

## 12. Известные пробелы и открытые вопросы

Пробелы:

1. **Пояснение подборки от ИИ.** Кнопки «объяснить» (`generateMatchReasons`) нет; у каждого решения
   показана причина совпадения из поиска («совпали направления…»).
2. **Порог подбора** откалиброван на 6 демо-проектах и 30 задачах. Нужна проверка на выгрузке
   реальных 993 проектов.
3. **Рабочий стенд** - миграции к его базе не применялись; нужен отдельный ОК на `migrate deploy`.
4. **Аудит помощника:** пишется только отправка оператору; создание потребности и ходы - нет.
5. **Сид:** `db:seed:demo` локально тянет код из `src/` (нужен `tsx` с хоста); в Docker
   (`Dockerfile.migrate` копирует `src/`) сид идёт автоматически после миграций при
   `SEED_DEMO=1`. Повторный запуск не сбрасывает дату передачи и заметки демо-запросов.
6. **Тёмная тема** - полная на основных экранах (каталог, карточка, дашборд, админка, помощник,
   лучшие практики); отдельные мелкие места (некоторые svg-иконки, редкие графики) ещё
   проверяются. Перевод темы в шапке - переключатель «Системная / Светлая / Тёмная».
7. **Казахская корректура** - интерфейс и терминология сведены к Termincom и внутреннему
   глоссарию (`docs/GLOSSARY.md`, в git не попадает), но полного вычитания носителем не было;
   ответы модели на kz - как есть. Замечания вычитки отправлять команде, фиксируются строкой
   в глоссарии.
8. **Временный стенд** - «холодный» старт после простоя (первый заход заметно медленнее),
    характер данных - временный; после показа стенд выключить или пересоздать.
9. **Целостность опубликованного контента** - правка представителем вуза уже живого решения
    без повторной модерации; ревизий/снапшотов в схеме нет. Требуется продуктовое решение
    (см. раздел 17).
10. ADMIN и EDITOR могут вести и отправлять потребности (для проверки); форма запроса на карточке - только у бизнеса.
11. Уведомлений (почта, Telegram) нет: оператор и вуз смотрят очередь сами.

Вопросы к постановщику:

- Правильно ли мы поняли «карточки» - это карточки решений, а не карточка потребности? План покрывает обе трактовки.
- Должен ли бизнес видеть заслушивания (замечания комиссии)? Сейчас - как `VIEWER`.
- Нужна ли продуктовая фаза D (B2B-поля карточки) и кто будет их заполнять для 993 проектов.
- Правовые вопросы из исходных документов (согласие на обработку ПДн, неразглашение, локализация данных) в коде не решались.
- Как в проде применяются миграции: сборка `prisma generate && next build` их не применяет - понадобится оформить `migrate deploy` на стенде.

## 15. Языки интерфейса: ru и kz

**Механика.** Язык интерфейса - `cookie` `lang`; читается на сервере (SSR), страница отдаётся
сразу на нужном языке, без «мигания» с русского на казахский. Переключатель «Рус / Қаз» в шапке
меняет cookie и перезагружает маршрут. Экспорт в Excel, поиск, помощник, админка - тоже на языке
интерфейса.

**Полнота.** Публичная часть, проекты, дашборд, вузы, поиск, админка, Excel-выгрузка, витрина
решений и помощник подбора - двуязычны полностью.

**Точечные решения.**

- Подписи технологий - по стабильным slug (`src/lib/technologies.ts`): на kz берётся написание из
  словаря (Termincom / внутренний глоссарий); у незнакомых (импортированных) технологий - исходное
  название из БД.
- Теги - словарь известных терминов с единой нормализацией (`ё→е`, схлопывание пробелов, нижний
  регистр, без `#`); незнакомые теги выводятся как ввёл пользователь. На странице теги не
  дублируются с точностью до регистра.
- Помощник подбора: вступление, вопросы (в т.ч. резервные, если модель недоступна), быстрые
  ответы-кнопки, сводка оператору - всё на языке интерфейса; модель получает указание генерировать
  вопросы на этом языке.
- ИИ-поиск: резюме («ЖИ-түйіндеме» на kz) и объяснения «почему совпало» генерируются на языке
  интерфейса; технологии в выдаче - на казахском на kz.
- Статус пилота - **«Қанатқақты жоба»**; «Жаңартылатын энергия» - по закону №165-IV (исключение
  из словаря Termincom).
- «QazInnovations» - единообразно в футере и контактах: полное наименование на kz и на ru.
- Excel-выгрузка («Дашборд»): заголовки, легенды и названия листов - на языке интерфейса.

Терминология сведена к Termincom (+ внутренние решения, зафиксированные в локальном
`docs/GLOSSARY.md`, который в репозиторий не попадает). Вычитки носителем не было - см. раздел 12, п. 7.

## 16. Что уходит в ИИ, что не уходит (санитизация ПДн)

Цель: персональные данные компании не попадают во внешнюю модель (Google Gemini). Как устроено:

| Поток | Что уходит в модель | Санитизация |
|---|---|---|
| Помощник подбора (`/business/assistant`) | Весь диалог (реплики компании и ответы ассистента) целиком, заново каждый ход | **Да**: `findSensitive()` выполняется ДО вызова модели. Детектируются: email / телефон (+7 / 8) / ИИН (12 цифр с проверкой даты рождения и контрольной цифры; БИН этим же фильтром отсекается; разделители внутри номера допускаются - «851231 4006 76» тоже ИИН) / номер карты (Luhn) / расчётный счёт IBAN Казахстана (mod-97-10, ISO 13616; допустимы пробелы и дефисы). Находка → ответ 422 с маскированными фрагментами, ход не засчитан, строка потребности не пишется |
| ИИ-поиск (`/api/ai-search`) | Сырой запрос + названия и описания до 10 проектов из выдачи | Нет - по дизайну: доступ только у ADMIN/EDITOR, поиск ведётся безличным каталожным запросом, ПДн туда не нужны |
| Генерация «AI-резюме» и объяснения «почему совпало» | То же, что в поиске | Нет |
| Excel-экспорт | В модель не уходит | - (локальная выгрузка файла) |
| LLM-кэш (`llm_cache`) | Исходный текст не хранится: `cacheKey` (хэши промпта и содержимого) и ответ модели | **Да** (по построению) |
| «Комментарий» и телефон в форме «Отправить оператору» | В модель не уходит; пишутся в `integration_requests`, видны оператору и вузу | Не требуется - это адрес назначения данных |

Что детектор ловит и не ловит. Ловит структурированные данные с контрольными цифрами,
включая номера, записанные с пробелами и дефисами (ложные срабатывания на БИН, бюджетах
и артикулах исключены и покрыты тестами).
**Не ловит:** имена, адреса, IBAN других стран (пока детектируется только
казахстанский формат) и обычные 20-значные расчётные счета, номера паспортов, названия компаний и
контрагентов - они уйдут в модель, если их явно напечатать. Памятка компании-клиенту:
«в чат - без персоналий и реквизитов; контакты подтянем из вашей учётной записи».

Помощник - единственный поток, где свободный текст компании уходит во внешнюю модель.
ИИ-поиск доступен только сотрудникам портала (ADMIN/EDITOR); компания им не пользуется.

**Юридическая оговорка.** Gemini на бесплатном уровне AI Studio - по условиям Google такие
промпты могут использоваться для улучшения продуктов. Для реального бизнес-конфиденциального
режима нужен платный ключ (и соглашение/DPA, если оно требуется стороне компании). На демо -
свободный тариф. Политика конфиденциальности на портале пока отсутствует (раздел 17).

### Риски фазы D

- **Фиктивный контент хуже отсутствия:** вузы поставят «закрытый контур» наугад → компании придут с прод-требованиями в несуществующий режим → репутационные потери обеих сторон.
- **Правовые риски:** «закрытый контур» и «стоимость» - заявления от имени вуза; нужны критерии заполнения и дисклеймер «заполнено вузом на дату X».
- **Перекос на пилотирование:** все форматы сведутся к «пилот», каталог теряет смысл как витрина внедрения.
- **Размывание формы:** 8+ полей + существующие → заполняемость падает; без автоматической разметки каталог не размечается.
- **Скрытый v1:** «пока без фильтров, просто показывать блок» - карточки размечаются, но никто на них не смотрит → брошенная работа.
- **Схема:** если позже поля вынесут в таблицу, миграция данных потребует аккуратного переноса; решение «сразу сделать нормально» дешевле переделки.

### Предлагаемый план v1 (после ответов на 6 вопросов)

2-3 недели: миграция + форма вуза + блок на карточке + 2 фильтра («формат», «контур») +
заполнение 10-20 демо-карточек + выверка kz-терминологии. Помощник и остальные фильтры - v2.
Старые карточки без полей показываются с меткой «условия не указаны» и не попадают под фильтр
«закрытый контур».

## 19. Риски переноса в основной репозиторий

Состояние на HEAD `f25648a`. Часть работы уже влита в `AdiEzzz/aisana` отдельными PR
(#4-#22, 12.11.2026): видимость неопубликованного, схемы тел, кэш ИИ, поиск, даты,
лимиты импорта, вход и сессии, файлы, `xlsx` 0.20.3, vitest. Эти правки адаптированы под
их npm, поэтому пакетный стек форка (pnpm, Docker, compose) не переносится. Ниже - то,
что осталось: B2B-ветка и изменения недели 16-19.11.

### A. Блокеры (без них перенос нельзя начинать)

1. **TLS на проде.** Cookie сессии переименована в `__Host-ai_map_sess` и ставится с
   `Secure` в production (`src/lib/auth.ts:9`, `login/route.ts`). По http:// браузеры её
   отбрасывают, и вход молча перестаёт работать. В их документации
   (`ПЕРЕД_ПУБЛИКАЦИЕЙ.md`) впереди заявлен nginx с сертификатом; переносить только после
   живого TLS.
2. **Права на `pgcrypto`.** Миграция `20261118130000_hash_session_tokens` выполняет
   `CREATE EXTENSION IF NOT EXISTS pgcrypto`. Если у их СУБД нет прав, `prisma migrate
   deploy` падает, `migrate`-контейнер завершается ошибкой, приложение не стартует
   (`depends_on: service_completed_successfully`). Отказ виден, но это простой. Варианты:
   ОК от их DBA заранее; ленивое перехэширование при логине без расширения; либо
   `DELETE FROM sessions` вместо перехэширования (все разлогинены, один раз).
3. **Том с PDF.** Точка монтирования меняется с `/app/public/uploads` на `/app/uploads_data`.
   Именованный том `uploads_data` тот же, поэтому файлы остаются и доступны по новому пути;
   ручной перенос нужен, только если у них bind-mount (`./uploads:/app/public/uploads`) или
   том переименован. Локальный стор лежит вне `public/`, раздача идёт только сессионным
   роутом с проверкой владельца (`src/lib/uploads.ts`, `LOCAL_UPLOADS_DIR`). URL и строки
   БД (`/uploads/файл.pdf`) не меняются. Если задан `BLOB_READ_WRITE_TOKEN` (Vercel Blob),
   локальный путь не используется; если их compose остаётся с локальным томом, поправить
   и путь монтирования.
4. **Спор по X-Forwarded-For.** Ветка берёт крайнюю правую запись
   (`src/lib/rate-limit.ts:148`, корректно за одним своим прокси). В основном репо берут
   первую (`78a5882`: за CDN правая запись - адрес CDN, общая корзина ретраев на всех).
   Переносить как есть нельзя: нужно решение владельцев инфраструктуры с учётом реальной
   схемы (nginx/CDN/прямые подключения). Рекомендация: сделать доверенный прокси
   конфигурируемым (`TRUSTED_PROXY_COUNT`) или вынести за флаг; не переносить `9de2b71`
   молча.

### B. Миграции и данные

5. **`hash_session_tokens`.** Просроченные сессии удаляются, живые перехешируются sha256
   на месте. `UPDATE` по всем строкам на большой таблице даёт краткую блокировку: делать
   в окно низкой нагрузки и после свежего дампа. Сессии в БД переживут миграцию, но вход -
   нет: cookie переименована, поэтому все один раз заходят заново (п. 10).
6. **Откат совместимости.** Старый образ сравнивает сырой токен и не узнаёт ни одну
   существующую сессию. Rollback = все заходят заново; сырые токены восстанавливаются
   только из дампа, данные приложения не теряются.
7. **Остальные 6 миграций аддитивны** (PG16): `ADD COLUMN` nullable / `IF NOT EXISTS`,
   `ADD VALUE` в enum, константный дефолт `false` у `availableForIntegration`, новые
   таблицы. Ветка проверена на чистой и на заполненной демо-БД.
8. **Срок хранения в `docker/backup.sh`.** Если переносить их бэкап-скрипт на нашу чистку,
   вместе с кодом пойдёт удаление `audit_logs` старше 365 дней и просроченных сессий при
   каждом бэкапе. Для них это тихая потеря чужих записей: согласовать срок до переноса
   (регуляторные требования могут требовать больше 365 дней); если срок другой, менять
   константу там же.
9. **Права дампов.** `umask 077` и `chmod 600` исправлены только для новых дампов;
   существующие файлы (если были 644) останутся открыты - прогнать `chmod` вручную.

### C. Runtime и поведение

10. **Все сессии протухают при переносе.** Cookie `ai_map_kz_session` в браузерах умирает
    сама, пользователи заходят заново. Ничего не сломается, но их саппорт получит волну
    «меня разлогинило»; предупредить заранее и выкатить в согласованное окно.
11. **Новый CSP `frame-ancestors 'self'`.** Заголовок запрещает встраивать портал в чужие
    iframe; если у них есть такие встройки, они сломаются. HSTS, `X-Frame-Options` и
    остальные заголовки уже есть в основном репо, их не трогаем.
12. **zod 3 → 4.** Ветка компилируется и проходит 158 тестов, но основная ветка под zod 4
    не пересобиралась. Находка `GHSA-mrhx-c7xc-m3w5` против zod ≤4.6.5 (CVSS 8.2) -
    спорная и отозвана как CVE 28.10.2026; апгрейд - гигиена, не security-fix. Переносить
    отдельным PR с обычным прогоном их CI, без слова «SECURITY».
13. **Модели Gemini по умолчанию изменены** (`gemini-3.6-flash` и новая цепочка). На их
    ключе доступность может быть другой, отсюда 404/429 при переносе. Перед выкаткой:

    из истории репозитория считать скомпрометированным и отозвать до слияния.
14. **`availableForIntegration` по умолчанию `false`.** После переноса витрина будет

15. **i18n - новый публичный слой `lang`-cookie.** С их middleware он не пересекается
